# 批次实现复盘（2026-11-07）

范围：#5–#10 的实现、双轴审查、批次修复和 `62bcf34` 门禁收尾。

## Findings（按严重性）

1. **验收记录滞后于实际门禁。** #5–#10 的记录先写入了“集成/E2E 延后”，完整门禁通过后才追加补充证据，容易让 issue 状态与真实证据脱节。
   - **措施：** 验收记录使用固定的“当前状态 / 最近门禁命令、日期、commit / 远程 CI / 剩余限制”字段；完整门禁完成后在同一交付步骤更新记录，再进行 issue 评论或关闭。
   - **自动化：** 增加文档检查，发现记录只有“延后/跳过”而没有最近完整门禁证据时失败。

2. **边界规格没有在首次实现时形成逐条测试矩阵。** 双轴审查发现了自申请替诊、紧急期限、未签到爽约、AI 重试、SSE 失败状态、退款结果通知和接诊时间窗口 7 个遗漏。
   - **措施：** 每个 issue 的 acceptance record 为每条 AC 指定一个可执行测试 seam；实现提交前逐行核对，审查时优先检查矩阵中没有测试的行。
   - **自动化：** 在验收文档检查中要求每条 AC 行包含测试或公共 seam，避免只写“已实现”。

3. **门禁运行期间修改了测试文件。** 一次完整验证使用了旧的测试编译结果，导致修复已写入但本轮仍失败，增加了排查时间。
   - **措施：** 启动 `scripts/verify.ps1` 后冻结工作树；若必须修改，先结束本轮门禁再重新启动。
   - **自动化：** 让验证脚本在开始和结束记录 `HEAD` 与工作树摘要，运行期间发生变化时退出失败并提示重新运行。

4. **本轮新增可靠性行为的直接测试仍偏少。** 全量门禁通过，但 AI 三次重试、SSE 投递失败转 `FAILED`、退款结果通知和后台爽约扫描没有各自独立的完整 HTTP 断言。
   - **措施：** 为每个审查修复补一条最小服务单测或 HTTP 用例，断言状态、attempts、错误码和通知 dedupe key，而不只依赖回归套件。

5. **本地证据与远程交付仍是两个步骤。** 本地门禁已经通过，远程 CI、PR 证据和 issue 评论尚未形成同一条交付记录。
   - **措施：** PR 流程固定为：推送分支 → 创建 PR → 等待远程 `verify.yml` 成功 → 将 run URL 和 commit 写入 acceptance record/issue 评论 → 再关闭已验证 issue。

- 双轴审查能发现跨模块规格偏差；后续应把审查发现沉淀为 AC 测试矩阵，而不是只依赖人工记忆。
